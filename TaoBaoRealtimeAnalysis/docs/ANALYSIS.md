# 样本分析与验证结论

## 数据范围及质量

2026-10-26 实测批次 `tb_20261026_105757`。取原始 CSV 前 10,000 行，按北京时间保留 2017-11-25 至 2017-12-03，共 9,997 条；日期范围外 3 条，无格式错误，无完全重复记录。五组 Flink 输出均与独立 Python 基准一致，详见 [原始对账报告](../reports/result.json)。

**分析判断：**这是按文件顺序取的样本，仅覆盖 92 个用户，不是总体随机抽样。对账证明这个样本的计算正确，不证明指标代表淘宝全部用户。后续应按用户随机抽样或完整处理数据，并检查日期、用户覆盖和数据缺失。

## 总体指标

|指标|实测值|
|---|---:|
|行为数|9,997|
|活跃用户|92|

|收藏次数|298|

|购买行为次数|179|

**分析判断：**浏览占行为约 89.86%，说明样本记录以浏览为主；179 次购买由 55 人贡献，平均每位购买用户约 3.25 次购买行为。59.78% 是观察期内购买用户占比，不是浏览到购买的因果转化率。数据没有订单号、金额、数量，不能推导 GMV、客单价或订单数。

**下一步：**用用户、商品和事件时间构建有先后顺序的浏览—加购—购买路径，定义归因窗口，再研究流失环节。不能直接把四类行为次数串成漏斗。

## 5 分钟窗口

共有 1,825 个非空窗口。看板展示每个窗口的 PV、独立用户和购买用户；窗口以北京时间左闭右开划分。

**分析判断：**短窗口适合观察短时波动，但这个样本量小，不能凭一两个峰值宣布异常或活动效果。跨窗口 UV 有重复用户，不能求和作为总 UV。监控应同时展示样本量，并与同星期、同时段的历史基线比较；当前项目未建立生产报警阈值。

## 每小时购买行为

95 个小时有购买记录；最高为每小时 5 次，多个小时并列，包括 2017-11-26 00:00 和 2017-11-27 10:00。

**分析判断：**最高值很小且有并列，尚不足以推荐最佳促销时间。需要更大样本，按小时同时比较活跃用户规模、购买用户占比和历史波动。仅按购买次数排名容易把流量差异误当成转化能力差异。

## 类目排行

有购买行为的类目 131 个，类目 835895、1620537 各 5 次，并列最高；965809 为 4 次。Top 10 仅用于展示，购买次数相同的类目按 ID 排序，不代表业务优先级差异。

**分析判断：**类目分散，头部优势在小样本中很弱。类目 ID 是匿名编码，没有可靠维表就不能命名为服装、美妆等。运营决策还需要曝光、购买人数、库存和金额；本数据不能计算利润贡献。

## 每日累计 UV

输出 1,296 个 10 分钟累计窗口，按自然日重置。次日 00:00 结束的窗口对应前一天的最终累计值，而次日 00:10 开始体现新一天。

**分析判断：**同一天的累计 UV 应单调不减，可用于观察用户覆盖速度；跨天可以回落，因为累计重置。回放按事件时间排序，播放速度是实验参数，不代表真实业务的增长速度。完整有界回放会结束所有窗口；持续流在事件时间停止推进后不会自动结束最后窗口。

## 迟到数据实验

见 [实验记录](../reports/late_experiment.json)。固定发送四条合成记录，顺序为 00:00、00:11、00:01、00:21；每条间隔 3 秒，让水位线推进。比较 5 秒与 20 分钟延迟容忍度。合成实验与真实样本使用不同主题，不混入用户数据。

**分析判断：**总量和窗口量可能不一致，必须把事件迟到作为排查项。更宽的水位线能容忍更晚到达的数据，但会延迟窗口出结果；这不是免费的精度提升。生产上应测量真实延迟分布、设定时效目标，并设计迟到补算/告警。本项目展示机制，不宣称解决全部乱序和故障恢复问题。

## 可复现边界

这次完成的是低资源实时分析实验：Kafka → Flink SQL → Kafka 结果 → 看板，以及独立基准验证。没有部署原参考项目的 Elasticsearch/Kibana/MySQL 维表，也没有跑完一亿条全量数据。单节点 Kafka 不具备高可用；内存排序、全局 distinct 状态和无认证私网看板均是学习环境选择，不能直接当生产系统使用。
